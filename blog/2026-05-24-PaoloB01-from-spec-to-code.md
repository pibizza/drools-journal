Last session was all design. This one was all code — and the gap between the
two is where the interesting things happen.

## The Listener That Already Existed

The first task: move journal writes out of `JournalledObjectStore` and
`JournalledNamedEntryPoint.beforeUpdate()` into a `JournallingRuntimeEventListener`.
The spec said to do it. The reason mattered: during restore, facts re-propagate
into Rete via `session.insert()`. If the listener isn't installed, no journal
records are produced. Clean re-propagation, no side effects.

We built `JournallingRuntimeEventListener` via TDD — three event handlers, one test
per behaviour. What I hadn't anticipated: `JournalledObjectStore` was carrying
`currentActivationId` state that the agenda reads to determine whether an insert is
logical. Moving the listener meant moving that state. Claude suggested a `LongSupplier`
or keeping it in the store; I pushed back. The state belongs in the listener. The
agenda resolves the listener lazily, the same pattern it already used for the store.

`JournalledObjectStore` after the refactor: a single `updateHandle()` override.
That's it. Fourteen lines including the license header.

## One Door In

The spec said `JournalledSessionFactory.open(kbase, storage, lambdaRegistry)`. I
looked at the `ModifyLambdaRegistry` parameter and said no. That's an implementation
detail. The caller should not manage it.

We talked it through. The lambdas in the registry are generated by the DRL compiler
and compiled into the KieBase's classloader. They're always available as long as the
KieBase exists — which it does, because you can't restore without one. The registry
gets built internally from the KieBase. The public API is just `open(kbase, storage)`.

Phase 5 (compiler rewrite) will add KieBase scanning to populate the registry
automatically. The API stays the same.

## The Safepoint That Wasn't There

TDD caught a real bug before the implementation was even finished.

We wrote the first tests for `RestoreEngine.scan()` the obvious way: insert a fact,
check it's in `survivingFacts`. The tests passed. Then I asked what a safepoint
actually means for the scan. Per spec: records accumulate in a pending buffer; a
`SafepointRecord` flushes them; anything trailing at end-of-scan is discarded.

Which means a fact inserted without a following safepoint should be discarded — it's
a post-crash partial write. Our tests were asserting the wrong thing.

We rewrote the tests to include safepoints, then added the failing test:

```java
void insertWithoutSafepoint_factIsDiscarded() {
    storage.append(new InsertRecord(1L, false, -1L, JournalPayloadBuilder.embed("hello")));
    // no SafepointRecord
    assertThat(result.survivingFacts()).isEmpty();
}
```

Red. Then we introduced the pending buffer and went green. The spec was right; the
first implementation was wrong; the test caught it.

## Runnables Were Overkill

The first version of the pending buffer used `List<Runnable>` — lambdas that captured
`survivingFacts` and would mutate it on flush. Claude wrote it. I looked at it and said
the obvious thing: we're buffering records, not actions. Use `List<JournalRecord>`.

```java
// before: lambda per record
pending.add(() -> survivingFacts.put(insert.factHandleId(), ...));

// after: record goes in directly
pending.add(record);
// flush applies in order
```

Simpler. No allocations beyond the list itself. The intent is clearer because the loop
that applies them reads exactly like the spec pseudocode.

## Where It Stops

Phase 1 is done: safepoint-buffered scan, surviving facts only. `firedMatches`,
`pendingTmsLinks`, `ModifyRecord` handling — none of that goes in until Phase 1.5
drives it via tests. The implementation stops exactly where the tests stop.

Phase 1.5 is next: bulk Rete re-propagation, the `oldToNew` translation map, and the
point where `ReplayFilter` starts caching `InternalMatch` objects. That's where the
restore protocol becomes a session.
